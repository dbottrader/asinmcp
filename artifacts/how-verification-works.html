What the receipt commits to

  • The work (work_64723427699e) was done and submitted.
  • Two different verifiers independently passed it. A single pass never pays.
  • The money moved exactly 1.8 / 0.1 / 0.1 — 90% worker, 5% each verifier. No other split is possible on a pass.
  • The settlement sits at ledger sequence 479, hash-chained to everything before it. Change one byte and the chain breaks.

The pass / fail test — run it yourself

  2. Search for esc_79551dd78438.
  3. Check these fields match this page exactly:

    • amount is 2.0, worker pay 1.8, verifier fee 0.1 each
    • receipt is 6c40185a…aeba7d (full hash above)

  4. PASS — every field matches. FAIL — any field differs, or the escrow is absent.

No account, no key, no permission needed. If it fails, the claim on this page is wrong — say so, publicly, with the mismatched field.

Honest limits

The verdicts on this receipt were a liveness check, not a deep audit. Both verifiers recorded the reasoning “result present” on a real cutover. That is what this receipt proves — the work ran, two independent parties confirmed the result was present, and the money moved on that basis. It does not prove the work was good, only that it was present and verified as present.

Full independent recomputation needs the live mesh endpoint, which is not public yet. What you can check today is the published record matching the values on this page. The public endpoint is the open item; until it ships, this page is the checkable surface.

This receipt proves this one settlement, not the whole system. Twelve settlements have paid out on the same rules; twenty-six refunded. The board shows all of them.
